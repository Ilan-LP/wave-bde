## Project overview

Wave BDE Platform is a solo-built internal platform for **Wave**, the BDE (student association) of Epitech Lyon. It replaces a fully manual, no-system current state. Two core drivers:

- A **point-based system** for the student bar (buvette) to push consumption and speed up service.
- A **global tracking layer** for treasury and member activity (todos).

## Architecture

- Single backend, single PostgreSQL database, serving **4 separate frontends**.
- Monorepo via pnpm workspaces with:
  - `apps/` — one app per frontend, plus the backend
  - `packages/` — shared code: API types, RBAC definitions, shared UI, auth client
- Deployed on a personal VPS via Docker Compose.

## Stack

- **Backend**: Express + Prisma + PostgreSQL
- **Frontends**: React + Vite + TypeScript + Tailwind
- **Auth**: JWT with refresh tokens, tied to the school email
- **Runtime**: Node.js >=22.13 (required by the pinned `pnpm@11.18.0` package manager via corepack; enforced in `engines`, CI, and the backend Dockerfile)

## The 4 frontends

1. **Public showcase site** — public-facing, no auth.
2. **Buvette (bar/checkout) site** — product buttons with point prices, a custom price field, a QR scanner button (points payment), a cash button (shows a change-counting helper), and a card button (triggers a SumUp card reader via the SumUp Cloud API). One purchase = one payment method only.
3. **Pole sites** (Communication, Events, Partenariats) — share a common template (todos, personal task space); each pole additionally gets custom, non-reusable modules for its specific needs (to be defined per pole later).
4. **Bureau (board) site** — full management back-office, including a private todo list not visible to anyone else.

## Points system

- Users buy points (top-up = money in); points are linked to the school email and identified via a per-user QR code.
- Spending at the buvette deducts points.
- Points can also be earned (e.g. via event participation; other methods TBD).
- This is a **distinct system** from the existing loyalty card program — do not conflate the two.

## Roles (RBAC) — 3 tiers

- **`BUREAU`** — full access to everything; the only tier that can correct point disputes/errors.
- **`RESPONSABLE_POLE`** — extended access on their own pole; can delegate cross-pole access to a member.
- **`MEMBRE_POLE`** — basic access on their own pole; targeted read access to shared data.

Pole todos can be assigned cross-pole (any BDE member can help another pole) but assignment is favored toward the pole's own members.

## Audit logging

Every mutating action must be logged from day one — transactions, point movements, role changes, deletions, everything. This is a **hard requirement**, not optional. Logs are exported daily via an automated job to Google Drive as a passive backup (no formal restore process required for now).

## Data model (Prisma schema)

Schema lives at `apps/backend/prisma/schema.prisma`, migrated via `prisma migrate dev` (first migration: `20260903205827_init`). All primary keys are `String @id @default(cuid())`, not autoincrement ints — sequential ints would make accounts guessable/enumerable via any endpoint that echoes an id back (JWT `sub`, login response, audit logs, etc.). Note: as of the QR code work (see **Per-User QR Code** below), IDs themselves are *not* what ends up embedded in QR codes — a separate opaque token is used instead, precisely so that an id leaking through one of those other channels can't be used to forge a QR.

**Models:**
- **`User`** — base identity for *anyone* in the system: BDE staff and plain students who just top up points at the buvette. Fields: email (unique), firstName, lastName, isActive, `passwordHash` (nullable — only set for `User`s that also have a `Member`; plain students never log in anywhere and never get one), timestamps. Optional 1:1 `Member`, optional 1:1 `PointsAccount`, 1:N `AuditLog` (as actor), 1:N `RefreshToken`.
- **`Member`** — extends `User` (1:1 via `userId`, `onDelete: Cascade`) for people who are actually part of the BDE. This is where RBAC lives: `role` (`MemberRole` enum), optional `poleId`. Also the anchor for Todo assignment/creation, PoleAccessGrant give/receive, and manual Transaction adjustments.
- **`Pole`** — `COMMUNICATION` / `EVENTS` / `PARTENARIATS` (enum `PoleType`, unique). Has Members, Todos, PoleAccessGrants.
- **`PoleAccessGrant`** — a `RESPONSABLE_POLE` delegating cross-pole access to a `Member`. Unique on `[memberId, poleId]`; both grantee (`memberId`, cascade) and pole (cascade) delete the grant, but the granting member (`grantedById`) does not (restrict).
- **`Todo`** — `status` (`TodoStatus`: TODO/IN_PROGRESS/DONE/BLOCKED), `scope` (`TodoScope`: PERSONAL/POLE/BUREAU). `poleId` is nullable at the DB level even though it's conceptually required when `scope = POLE` — **that constraint is enforced in application code, not the DB.** `assigneeId` is `SetNull` on delete (todo survives, becomes unassigned); `creatorId` is required and restricted (can't delete a Member who has created Todos without reassigning first).
- **`PointsAccount`** — 1:1 with `User` (cascade), `balance` (Int, default 0). 1:N `Transaction`. `qrToken` (String, nullable, unique) + `qrTokenExpiresAt` (DateTime, nullable) hold the current buvette-scan QR token; see **Per-User QR Code** below. Added in migration `20260907154756_add_points_account_qr_token`.
- **`Transaction`** — signed `amount` (Int; positive = credit, negative = debit), `type` (`TransactionType`: TOPUP/PURCHASE/EVENT_REWARD/ADJUSTMENT/REFUND), `metadata` (Json, nullable — SumUp refs, QR scan data, event id, etc.), optional `performedById` (only set for manual staff adjustments). Indexed on `[pointsAccountId, createdAt]` for account history queries.
- **`Product`** — buvette catalog item: `name`, `pricePoints` (Int, matching the `amount`/`balance` convention of storing points as plain integers), `isActive` (Boolean, default true, same retire-without-delete pattern as `User`/`Member` — a retired product survives so past `Transaction`s referencing it stay intact once that link exists), timestamps. No relation to `Pole` (the buvette isn't pole-scoped) or `Transaction` yet — this model is schema-only for now; wiring a real purchase (`Transaction.productId` or similar) is Build Order step 2, not done here. Added in migration `20260907145039_add_product`.
- **`RechargeCheckout`** — one row per self-service recharge attempt (`POST /me/recharge`, see **SumUp Integration + Recharge**): a SumUp hosted checkout tied to a `PointsAccount`, with `points`/`amountMinorUnit`/`currency` and a `status` (`RechargeCheckoutStatus`: PENDING/CONFIRMED/FAILED/EXPIRED) that only ever moves forward once, via a conditional `updateMany` guarded on `status: "PENDING"` — the same race-safety idiom `Transaction`'s balance deduction already uses. `sumupCheckoutId` is unique so a given SumUp checkout can only ever back one row. Added in migration `20260911105455_add_recharge_checkout`.
- **`AuditLog`** — `actorId` is nullable + `SetNull` on delete **on purpose**: the log must outlive the user it references. Indexed on `[entityType, entityId]` and `[createdAt]`.
- **`AuditExportCursor`** — singleton row (`id` fixed to the literal `"singleton"`) tracking how far the daily Google Drive export has gotten; see **Audit Log Export** below.
- **`RefreshToken`** — one row per issued refresh token; see **Authentication** below.

Every FK column is now covered by an index (either a dedicated `@@index` or, where it's already the leading column of a `@@unique`/composite index, that): `Member.poleId`, `PoleAccessGrant.poleId`/`grantedById`, `Todo.poleId`/`assigneeId`/`creatorId`, `Transaction.performedById`, `AuditLog.actorId` (migration `20260903211613_add_fk_indexes`), and `RefreshToken.userId` (migration `20260903211625_add_password_hash_and_refresh_token`, added alongside the `RefreshToken` table itself).

**Why `User`/`Member` are split:** every human who touches the system becomes a `User` (a student buying a coffee needs an identity + points account, nothing else). Only actual BDE staff get a `Member` row layered on top, carrying the RBAC role and pole assignment. This keeps the 3-tier RBAC (see below) from leaking onto the thousands of students who are just customers.

**Why `Role` is a Prisma enum, not a table:** the 3-tier RBAC (`BUREAU` / `RESPONSABLE_POLE` / `MEMBRE_POLE`) is fixed and not meant to be DB-editable — no admin UI for creating custom roles is planned. An enum is simpler and gets compile-time exhaustiveness checks; revisit only if the RBAC model itself changes.

**Gotchas:**
- `isActive` flags on `User`/`Member` are there for planned soft-delete — the app layer should prefer flipping `isActive` over hard-deleting rows. The cascade/`SetNull` rules above are already set up with that in mind (e.g. `AuditLog.actorId` survives user removal); don't add hard-delete flows that fight this.
- Running Prisma commands locally requires `apps/backend/.env` (gitignored, not committed) with `DATABASE_URL` pointing at the docker-compose Postgres (`postgresql://wave:wave_dev_password@localhost:5432/wave_dev` by default) — copy from `apps/backend/.env.example`.
- The Prisma CLI loads `.env` itself, but the running app never did — it only ever read `PORT`, so this was invisible. Now that the app validates `JWT_SECRET`/`JWT_REFRESH_SECRET` at startup (see **Authentication**), `pnpm dev` loads `apps/backend/.env` via Node's native `--env-file=.env` flag (in the `dev` script) — no `dotenv` dependency added. Docker/production get real env vars injected directly by `docker-compose.yml`, so they don't need this.
- `pnpm-workspace.yaml` has an `allowBuilds` allowlist (pnpm's supply-chain gate for postinstall scripts) — `@prisma/client`, `@prisma/engines`, and `prisma` are set to `true` there so `pnpm install` can fetch Prisma's query engine binaries. Any future package with a build script will need the same treatment or its build gets silently skipped.

## Authentication

Implemented in `apps/backend/src/routes/auth.ts`, `src/lib/jwt.ts`, `src/lib/password.ts`, `src/lib/prisma.ts`, `src/config/env.ts`.

- **Who can log in**: a `User` whose `passwordHash` is set (bcryptjs, 12 salt rounds) **and** who has an active `Member` (role/pole come from `Member`, not `User`). Plain students (no `Member`) can never log in — they only ever get scanned via QR at the buvette. `isActive` is checked on both `User` and `Member`; any failure returns a generic `401 { error: "invalid credentials" }` to avoid leaking which emails exist. This is timing-safe too: when the user/member lookup fails before a real password hash exists, `verifyDummyPassword` (`src/lib/password.ts`) still runs one bcrypt comparison against a fixed dummy hash, so a nonexistent/inactive account and a valid-email/wrong-password attempt take the same time — otherwise the early return was a measurable side-channel for enumerating registered emails.
- **Email lookup is case-normalized**: `/auth/login` lowercases and trims the submitted email (`rawEmail.trim().toLowerCase()`) before the Prisma lookup, since `User.email`'s unique index is case-sensitive at the DB level. This only fixes the read side — nothing yet normalizes email casing at write time, since there's no user-creation endpoint (see the "Known gap" below); any future creation/seed flow must lowercase on insert too, or the two sides can still drift.
- **Access token**: JWT, HS256 (algorithm pinned explicitly on both sign and verify — `{ algorithms: ["HS256"] }` — as defense-in-depth, not because anything asymmetric exists in this app today), signed with `JWT_SECRET`, 15 min expiry. Payload: `{ sub: userId, memberId, role, poleId }` — enough for a future RBAC middleware to authorize without a DB hit. **Accepted tradeoff**: because `authenticate`/`requireRole`/`requirePoleAccess`'s BUREAU-bypass and native-pole paths never hit the DB, a role change, pole reassignment, or deactivation doesn't take effect for an already-issued access token until it expires — up to 15 minutes. This is an intentional stateless-JWT tradeoff for this project's size, not an oversight; revisit (e.g. a `tokenVersion` column checked in `authenticate`) only if that window becomes unacceptable.
- **Refresh token**: *also* a JWT (same HS256 pinning), signed with a separate secret (`JWT_REFRESH_SECRET`), 30 day expiry, payload `{ sub: userId, jti }`. The JWT itself is never trusted alone — only its SHA-256 hash, looked up against `RefreshToken.tokenHash`, determines whether it's still valid (unrevoked, unexpired, unrotated — `/auth/refresh` checks `RefreshToken.expiresAt` explicitly as a DB-side backstop, independent of the JWT's own `exp`). Both tokens are returned in the JSON response body (not cookies — avoids pulling in `cors`/cookie middleware, which is out of scope; storing the refresh token in an httpOnly cookie is a documented future hardening step once the frontends need cross-origin cookie handling).
- **Rotation**: every `POST /auth/refresh` call issues a brand-new access+refresh pair and revokes the presented refresh token (`revokedAt` + `replacedByTokenId` linking the chain), done inside a Prisma interactive transaction. The revoke is a conditional `updateMany({ where: { id, revokedAt: null } })` checked for `count === 0` *inside* that same transaction (not a separate read-then-write) — this closes a race where two concurrent refreshes of the same token could otherwise both succeed before either observed the other's revoke, silently doubling a session without tripping reuse-detection.
- **Reuse/theft detection**: presenting a refresh token that's already `revokedAt` (i.e. already rotated away, logged out, or lost the rotation race above) revokes **every** active refresh token for that user, not just the one presented — treats reuse as a stolen-token signal.
- **Logout** (`POST /auth/logout`): revokes just the presented refresh token. Idempotent — a missing/garbage/already-revoked token still returns `204`.
- **Rate limiting**: `POST /auth/login` is limited to 10 attempts per 15 minutes per IP; `POST /auth/refresh` and `POST /auth/logout` share a looser 30-attempts-per-15-minutes limiter (`express-rate-limit`, in-memory store — fine for a single-instance VPS deployment; revisit if the backend is ever horizontally scaled, since the counter wouldn't be shared across instances). Both limiters are constructed fresh inside `createApp()` (see **Security hardening**), not at module scope, so each app instance gets its own in-memory state.
- **Required env vars** (fail-fast, `src/config/env.ts`, imported first thing in both `src/app.ts` and `src/index.ts`): `JWT_SECRET`, `JWT_REFRESH_SECRET`. Missing or empty → the server throws and refuses to start, before any request is served. Generate real values with `openssl rand -hex 32`. **Enforced, not just documented**: `env.ts` also throws if the two secrets are equal — "never reuse the same value for both" used to be convention only.
- **Known gap**: there is no endpoint or seed script to *create* a `Member`'s initial password — `passwordHash` currently has to be set directly in the DB (e.g. via Prisma Studio or a one-off script) for local testing. An invite/registration/password-reset flow is a separate future task.
- **Implemented**: RBAC/authorization middleware lives in `src/middleware/` — see **RBAC Middleware** section below.
- **Tests**: `src/__tests__/routes/auth.test.ts` (Vitest + Supertest, Prisma and `src/lib/password.ts` mocked) covers the timing-normalization call, the DB-side expiry check, the rotation-race rollback, reuse/theft detection, logout idempotency, and email case/whitespace normalization. `src/__tests__/config/env.test.ts` covers `env.ts`'s fail-fast behavior (missing/empty secrets, identical secrets) via `vi.resetModules()` + dynamic re-import per case.

## RBAC Middleware

Implemented in `apps/backend/src/middleware/authenticate.ts`, `src/middleware/rbac.ts`, `src/middleware/index.ts`. Types in `src/types/express.d.ts`. Tests in `src/__tests__/middleware/rbac.test.ts` (Vitest + Supertest — no running database required; Prisma is mocked).

**Two-layer design:**

1. `authenticate` — verifies the Bearer token and attaches `req.auth: AccessTokenPayload`. Always required first on any protected route. Stateless, no DB hit.
2. Composable factory middlewares, applied per route after `authenticate`:
   - `requireRole(...roles: MemberRole[])` — passes if the caller's role is in the list. **BUREAU always bypasses this check** (hardcoded). Returns 403 otherwise.
   - `requirePoleAccess()` — passes if the caller has access to the pole in `req.params.poleId`. Check order: BUREAU bypass (no DB) → native `poleId` match (no DB) → `PoleAccessGrant` DB lookup. Returns 403 if none match.

**How to protect a route:**

```ts
import { authenticate, requireRole, requirePoleAccess } from "../middleware/index.js";

// BUREAU-only:
router.post("/adjustments", authenticate, requireRole("BUREAU"), handler);

// Any logged-in member:
router.get("/todos", authenticate, requireRole("RESPONSABLE_POLE", "MEMBRE_POLE"), handler);

// Pole-scoped (native membership + delegated grants):
router.get("/poles/:poleId/todos", authenticate, requirePoleAccess(), handler);

// Stack both (role check first, then pole access):
router.post("/poles/:poleId/todos", authenticate, requireRole("RESPONSABLE_POLE", "MEMBRE_POLE"), requirePoleAccess(), handler);
```

**Cross-pole delegation:** `requirePoleAccess()` does a single `prisma.poleAccessGrant.findUnique({ where: { memberId_poleId: { memberId, poleId } } })`. The grant can be time-bounded via `expiresAt` — expired grants are rejected silently. The DB hit is skipped for BUREAU and for users on their own pole.

**Running tests:** `pnpm --filter @wave/backend test` or `cd apps/backend && pnpm test`. No database needed.

**Gotchas:**
- Always chain `authenticate` before any RBAC middleware — both factories return 401 defensively if `req.auth` is missing, but `authenticate` must always run first in production.
- `requirePoleAccess()` reads `req.params.poleId` — routes using it must include `:poleId` in the path, otherwise it returns 400.
- BUREAU bypass is hardcoded in both factories. Do not try to restrict BUREAU via these middlewares — the spec defines BUREAU as full-access.

## Per-User QR Code

Implemented in `apps/backend/src/lib/qrToken.ts` (payload generation) and `apps/backend/src/routes/me.ts` (the endpoint), mounted in `src/app.ts` via `app.use("/me", meRouter)`. Tests in `src/__tests__/routes/me.test.ts` (Vitest + Supertest, Prisma mocked — no running database required).

**Scope:** this covers QR *generation* and *retrieval* only. The buvette scan/deduction endpoint that consumes this payload is `POST /buvette/scan` — see **Buvette Scan + Deduction** below.

**What the QR encodes:** an opaque, randomly-generated token (`crypto.randomBytes(32)`, base64url, prefixed `wave:v1:`) — deliberately **not** the raw email and **not** the `User`/`PointsAccount` id. Both of those already appear elsewhere in the API (JWT `sub` claim, `/auth/login`'s response body, audit logs), so encoding either one in the QR would add no real protection: anyone who obtained the id or email through any of those other channels could fabricate a working QR by hand, without ever seeing the person's real badge. The token lives on `PointsAccount.qrToken`, decoupled from any identifier that's exposed anywhere else.

**Rotating, not static:** the token has a 5-minute TTL (`PointsAccount.qrTokenExpiresAt`, `QR_TOKEN_TTL_MS` in `qrToken.ts`). `GET /me/qrcode` returns the current token unchanged (no DB write) if it hasn't expired yet, or generates and persists a fresh one if it's missing or expired. This bounds how long a QR stays usable if someone photographs/screenshots it — `POST /buvette/scan` rejects an expired token even if it otherwise matches. There is no manual regenerate/revoke endpoint (out of scope for this task); the TTL is the only invalidation mechanism today.

**Endpoint:** `GET /me/qrcode`, behind `authenticate` only (no role restriction — any authenticated caller can fetch their own QR, nobody else's). Looks up the `PointsAccount` for `req.auth.sub`; **404** `{ error: "points account not found" }` if the caller has none (there's no PointsAccount-creation flow yet — inventing one was out of scope here). On success: `{ qrPayload: "wave:v1:<token>", expiresAt: "<ISO>" }`. This is the first "self-service" (`/me/...`) route in the codebase — a convention future self-service endpoints can follow.

**Response is a raw payload, not an image:** the endpoint returns the string to encode, not a rendered QR image, so no QR-image-generation dependency was added to the backend. Rendering it as an actual scannable QR code is a frontend concern for whichever future task builds the buvette-facing display — not built here.

**Known gap:** only `Member`s can authenticate today (see **Authentication**), so in practice only BDE staff can currently reach this endpoint. Plain students — the primary buvette customers, who have no `Member`/password and never log in — have no way yet to self-retrieve their own QR code. This isn't fixable within this task: there's no student account-creation flow either (see **Open questions**, "Initial password / Member creation flow" — that gap now extends to plain students needing some way to receive/view their QR at all, not just Members needing a password).

## Product Catalog

Implemented in `apps/backend/src/routes/products.ts`, mounted in `src/app.ts` via `app.use("/products", productsRouter)`. Tests in `src/__tests__/routes/products.test.ts` (Vitest + Supertest, Prisma mocked). Added alongside the buvette cashier frontend (see **Buvette Cashier Frontend**) — the `Product` model existed since migration `20260907145039_add_product`, but nothing served it until the till needed a catalog to render product buttons from. A second pass (2026-09-11) added the management CRUD endpoints below — the `Product` model itself needed no schema change, since `isActive` already existed for the retire-without-delete pattern.

**Till-facing endpoint (unchanged):** `GET /products`, behind `authenticate` + `requireRole("RESPONSABLE_POLE", "MEMBRE_POLE")` — same "any logged-in member" RBAC shape as `POST /buvette/scan` below (BUREAU bypasses automatically). Returns `{ products: [{ id, name, pricePoints }] }`, filtered to `isActive: true` and ordered by name. No pagination — the buvette catalog is expected to stay small.

**Management endpoints (BUREAU-only):** product management belongs to full bureau access, not day-to-day till operation, so every route below is `authenticate` + `requireRole("BUREAU")` — since `requireRole`'s BUREAU-bypass is hardcoded, listing only `"BUREAU"` correctly restricts to that tier alone (see **RBAC Middleware**).

| Method | Path | Body | Response |
|---|---|---|---|
| GET | `/products/all` | — | `{ products: [{ id, name, pricePoints, isActive }] }` — all products, active and inactive, ordered by name |
| POST | `/products` | `{ name, pricePoints }` | `201 { product: { id, name, pricePoints, isActive } }` — `isActive` always `true`, not settable on create |
| PATCH | `/products/:id` | `{ name?, pricePoints? }` (at least one required) | `{ product: {...} }` |
| PATCH | `/products/:id/active` | `{ isActive: boolean }` (required) | `{ product: {...} }` |

**Active-only vs. all — separate endpoint, not a query param:** `GET /products/all` (BUREAU-only) is a distinct route from `GET /products` (any-member, active-only) rather than a query flag on the same one. Every route in this codebase uses a fixed, declarative RBAC middleware chain — none branch the required role at runtime off a query param — so making "all vs. active" a query flag would mean one route needing two different role checks depending on input. A separate route keeps both chains static and leaves the till's existing `GET /products` call completely untouched.

**Toggle-active is an explicit set, not a flip:** `PATCH /products/:id/active` takes `{ isActive: boolean }` rather than reading the current value and inverting it server-side. An explicit set is idempotent and race-safe — two BUREAU members toggling near-simultaneously can't fight over which one's stale read wins — consistent with this codebase's general preference for explicit conditional updates (see the balance-deduction pattern in **Buvette Scan + Deduction**).

**No hard delete.** There is deliberately no `DELETE /products/:id` — retiring a product is `PATCH /products/:id/active` with `{ isActive: false }`, matching `isActive`'s documented retire-without-delete purpose (see **Data model**'s `Product` entry): a hard delete would risk orphaning any future `Transaction`→`Product` link once one exists (`buvette.ts` currently records product data by value into `Transaction.metadata`, not a FK — see **Buvette Scan + Deduction** — but the retire-not-delete convention is kept anyway for when that FK lands).

**Not-found handling:** `PATCH /products/:id` and `PATCH /products/:id/active` both do a `findUnique` first and return `404 { error: "product not found" }` if missing, before attempting the update — same shape as `buvette.ts`'s `productId` 404 path.

**Audit logging:** no manual `auditLog` calls. Because every management route is mounted flat under `/products`, the middleware's automatic entity-type inference (`Product`) is already correct, and both `PATCH` routes get `entityId` for free from `req.params.id`. Only `POST /products` sets `res.locals.auditEntityId` explicitly — its response is wrapped as `{ product: {...} }` rather than a flat body with a top-level `id`, so the middleware's `responseBody.id` inference fallback wouldn't otherwise find one (same reasoning as `POST /buvette/scan`'s explicit override, see **Audit Logging**'s "Known limitation").

**Not built here:** any frontend for product management — the bureau site (`apps/bureau`) remains a scaffolded shell with no real UI yet; these are backend endpoints only, for a future bureau-site screen to call.

## Buvette Scan + Deduction

Implemented in `apps/backend/src/routes/buvette.ts`, mounted in `src/app.ts` via `app.use("/buvette", buvetteRouter)`. Tests in `src/__tests__/routes/buvette.test.ts` (Vitest + Supertest, Prisma mocked — no running database required).

**Scope:** points-only. This is the first slice of Build Order step 2 — the SumUp/card payment path is a separate, not-yet-built future task, and so is a recharge/top-up endpoint. The buvette cashier frontend that calls this endpoint is built — see **Buvette Cashier Frontend**.

**Who is who:** the caller authenticated via the JWT (`authenticate`, `req.auth`) is the **BDE Member operating the till**, not the person paying. The **paying customer** is identified purely by the scanned QR payload in the request body and resolved server-side to a `User`/`PointsAccount` — `req.auth` is never treated as the customer's identity.

**Endpoint:** `POST /buvette/scan`, behind `authenticate` then `requireRole("RESPONSABLE_POLE", "MEMBRE_POLE")` (BUREAU bypasses automatically, per the usual RBAC convention — this is the "any logged-in member" shape, since buvette isn't pole-scoped and every `MemberRole` value passes). Request body: `{ qrPayload: string, productId?: string, customAmount?: number, quantity?: number }` — **exactly one** of `productId` or `customAmount` is required (both or neither → 400); this covers the cashier frontend's "custom price" fallback for items not in the fixed product list, since there was otherwise no way to charge an arbitrary points amount via QR/points payment. `quantity` (defaults to `1`, must be a positive integer) is only valid alongside `productId` — supplying it with `customAmount` is 400, since a custom sale is a single total amount, not a per-unit price × count. `customAmount` itself must be a positive integer if present. On success: `201 { transactionId, product, quantity, amountDeducted, newBalance, customerUserId }` — for a `productId` sale, `product` is `{ id, name, pricePoints }` and `quantity` is the resolved count; for a `customAmount` sale, both are `null` and `amountDeducted` is the custom amount as-is (no quantity multiplication).

**QR validation:** `prisma.pointsAccount.findUnique({ where: { qrToken: qrPayload } })`, then check `qrTokenExpiresAt` is set and in the future — same token/TTL contract as **Per-User QR Code** above. Not-found and expired collapse into the same generic `401 { error: "invalid or expired qr code" }`, mirroring `/auth/login`'s "invalid credentials" anti-enumeration approach — the response never reveals which reason applied.

**Error responses (all reject with no partial state change):**
| Case | Status |
|---|---|
| malformed body (missing `qrPayload`; missing/both of `productId`/`customAmount`; invalid `quantity`/`customAmount`; `quantity` alongside `customAmount`) | 400 |
| QR not found or expired | 401 |
| product doesn't exist (`productId` path only) | 404 |
| product exists but `isActive: false` (`productId` path only) | 409 |
| balance too low (including losing a concurrent-scan race) | 402 |
| replay guard / general throttle tripped | 429 |

**Atomicity ("no partial deduction"):** mirrors `auth.ts`'s refresh-token rotation race-safety pattern exactly (see **Authentication**) — inside `prisma.$transaction`, a conditional `pointsAccount.updateMany({ where: { id, balance: { gte: totalPrice } }, data: { balance: { decrement: totalPrice } } })` is checked for `count === 0` (insufficient balance, or a concurrent scan won the race) and rolled back via a thrown+caught sentinel error before the `Transaction` row is ever created. Either both the balance change and the ledger row land, or neither does.

**Anti-fraud (explicit, basic checks only):**
1. QR expiry/opacity validation above rejects tampered/guessed/stale tokens.
2. A replay/duplicate-scan guard: the exact same `qrPayload` string can only be attempted once per 3 seconds (`buvetteQrReplayRateLimit` in `app.ts`, keyed on the request body rather than IP — see below). Catches an accidental double-submit or an attacker replaying a captured QR image seconds later, without blocking legitimate back-to-back different purchases.

Deliberately **not built**: no ML/behavioral fraud scoring, no device fingerprinting, no cross-account velocity checks. Revisit only if the two checks above prove insufficient in practice.

**Rate limiting:** two `express-rate-limit` instances (already a dependency — no new package added), constructed inside `createApp()` and applied via `app.use("/buvette/scan", ...)` before the router mount, same pattern as `loginRateLimit`/`refreshLogoutRateLimit`:
- `buvetteScanRateLimit` — general throttle, **per-IP** (default keyGenerator), 30 requests/min. Guards against a runaway till client or a compromised operator session.
- `buvetteQrReplayRateLimit` — the anti-fraud replay guard above, **per scanned-QR-value** (custom `keyGenerator` reading `req.body.qrPayload`), 1 request/3s. Falls back to `ipKeyGenerator(req.ip)` (not raw `req.ip`) when the body is missing/malformed — required by `express-rate-limit` v8, which throws `ERR_ERL_KEY_GEN_IPV6` if a custom `keyGenerator`'s IP fallback isn't wrapped that way.

Both need `req.body` (available since `express.json()` runs globally before them) but not `req.auth`, so they sit at the `app.use(path, ...)` level like the auth limiters, ahead of `authenticate` inside the router — no ordering conflict.

**No schema changes.** `Product` still has no relation to `Transaction` (this was deliberately deferred — see **Data model**). Rather than add a migration, the product id/name/quantity/unit price (or, for a `customAmount` sale, `{ customAmount: true, amountPoints }`) are recorded in `Transaction.metadata` (the `Json?` field whose doc comment already calls out "QR scan data" as an intended use). The scanned QR isn't stored raw there — only a SHA-256 hash (`qrTokenHash`) — because the token doesn't rotate on use and stays valid for the rest of its 5-minute TTL, so persisting it verbatim would leave a still-usable credential sitting in the ledger; same reasoning as `RefreshToken.tokenHash` (see **Authentication**). Separately, `"qrPayload"` was added to `audit.ts`'s `REDACTED_KEYS` denylist (see **Audit Logging** below) so the raw value the operator's client actually posted doesn't get captured into `AuditLog.metadata.requestBody` (and from there into the Drive export) by the generic audit middleware.

**`Transaction.performedById` is left `null`** for these purchases. CLAUDE.md documents this field as only meaningful for manual staff `ADJUSTMENT`s; a buvette `PURCHASE` isn't that, so setting it would repurpose a field with narrower documented semantics. Which operator ran the till is already captured by the audit log's `actorId` (the operator's `User.id`, from `req.auth.sub`) — no loss of traceability.

**Audit logging:** no ad-hoc logging call — relies entirely on the existing global `auditLog` middleware. Because the route is mounted under `/buvette` (first path segment ≠ the mutated entity), the handler explicitly sets `res.locals.auditEntityType = "Transaction"` and `res.locals.auditEntityId = transaction.id` before responding, per the override mechanism documented in **Audit Logging**'s "Known limitation".

## Audit Logging

Implemented in `apps/backend/src/middleware/audit.ts` (exported as `auditLog` from `src/middleware/index.ts`), wired globally in `src/app.ts` via `app.use(auditLog)` right after `app.use(express.json(...))`, before any router. Tests in `src/__tests__/middleware/audit.test.ts` (Vitest + Supertest, `prisma.auditLog.create` mocked — no running database required).

**How it works:** every `POST`/`PUT`/`PATCH`/`DELETE` request is logged automatically, with no per-route call needed — the middleware hooks `res.on("finish")` early in the chain, then reads `req.auth` (set later by that route's `authenticate`, if any) once the response has actually finished. It writes one `AuditLog` row via:
- `actorId`: `req.auth?.sub ?? null` (matches `User.id`).
- `action`: `CREATE` (POST) / `UPDATE` (PUT, PATCH) / `DELETE` (DELETE).
- `entityType`: inferred from the first path segment (kebab-case → PascalCase, naive trailing-`s` stripped, e.g. `/points-accounts` → `PointsAccount`).
- `entityId`: `req.params.id` if present, else the response body's `id` field, else the literal string `"unknown"` (with a `console.warn`) — a row is always written, never silently dropped for lack of an id.
- `metadata`: `{ method, path, role, requestBody, responseBody }` — both bodies redacted (keys `password`, `passwordHash`, `token`, `accessToken`, `refreshToken`, `tokenHash`, `newAccessToken`, `newRefreshToken`, `secret`, `apiKey`, `authorization`, `qrPayload` become `"[REDACTED]"`; `qrPayload` was added for **Buvette Scan + Deduction** below, the first route to post a live short-TTL credential in its body). This is a fixed key-name denylist, not structural — a future route storing a secret under a different field name won't be caught automatically; extend `REDACTED_KEYS` in `audit.ts` when that happens. There's no dedicated `role` column on `AuditLog`, so role rides in `metadata` instead — a deliberate choice, not a schema gap. `redact()` special-cases `Date` values (serializing to ISO strings) before its generic array/object recursion — without that, any `Date` field on a Prisma record echoed back in a response body (nearly every model has `createdAt`/`updatedAt`) would silently collapse to `{}`, since `Object.entries(new Date())` returns no own enumerable properties.

**Only successful mutations are logged** (`res.statusCode < 400`) — a rejected request didn't actually change anything, so it isn't recorded as an audit entry.

**Excluded automatically:** `/auth/*` and `/health`. Auth routes mutate `RefreshToken` rows but that's already self-documented there (`revokedAt`/`replacedByTokenId`); the audit log stays scoped to business-entity mutations.

**To exclude or override a route without touching the middleware:**
- `res.locals.skipAudit = true` — skips audit logging entirely for that route.
- `res.locals.auditEntityType` / `res.locals.auditEntityId` — override automatic inference (needed for non-flat routes, e.g. a future nested resource like `POST /points-accounts/:id/transactions`, where the mutated entity isn't the first path segment).

**Error handling:** the audit write is fired from inside the `finish` handler, after the response has already been sent, and is never awaited by the request — a DB/logging failure cannot block or fail the business response. On failure it's `console.error`'d (never silently swallowed) so a missed log is visible in server logs even though the client never sees it.

**Known limitation:** entity-type/id inference only looks at the first path segment and `req.params.id`, so it silently mislabels nested routes — including CLAUDE.md's own documented RBAC example, `POST /poles/:poleId/todos`, which would get audited as `entityType: "Pole"` instead of `"Todo"`. `audit.test.ts` has a test pinned to this exact scenario (`"KNOWN LIMITATION: mislabels entityType..."`) so the wrong-but-expected behavior is visible and won't silently change — any real route shaped like this **must** set `res.locals.auditEntityType`/`auditEntityId` explicitly (see below). There's also no generic DB "before" snapshot: `metadata.requestBody` is the client's change payload, not a true prior-row read — building one generically would require mapping each inferred `entityType` back to a Prisma delegate, which is unverified against any real route since none exist yet. If a future route needs a real before/after diff, have that handler set `res.locals.auditBefore` before responding and extend the middleware to include it (not currently implemented).

**Coverage right now:** `POST /buvette/scan` (see **Buvette Scan + Deduction** above) is the first live route to actually produce an audit row — every other mutating route (`/auth/login`, `/auth/refresh`, `/auth/logout`) is excluded by design above. The middleware applies automatically the moment any future business mutating route is added; no wiring needed per route beyond the `res.locals.auditEntityType`/`auditEntityId` override for non-flat paths.

## Audit Log Export

Implemented in `apps/backend/src/jobs/googleDrive.ts` (auth + upload), `src/jobs/auditLogExport.ts` (the export itself), and `src/jobs/scheduler.ts` (daily timing). Started once from `src/index.ts` (`scheduleDailyAuditExport()`) — deliberately **not** from `src/app.ts`/`createApp()`, so no background timer is ever spun up by `createApp()`-based tests. Tests: `src/__tests__/jobs/{googleDrive,auditLogExport,scheduler}.test.ts` (Vitest, Prisma, `google-auth-library`'s `JWT`, and the global `fetch` all mocked — no real network/DB/Google credentials needed to run the suite).

**Scope:** this is a passive backup, not a restore system — there is no import/restore tooling, and none is planned. Out of scope: a UI/dashboard for export history, and a retention/cleanup policy for old export files in Drive (nothing ever deletes them).

**Schedule:** a hand-rolled recursive-`setTimeout` scheduler (no cron library — a single fixed daily slot didn't justify a new dependency), firing at **03:00 UTC** every day. Recursive `setTimeout` rather than `setInterval` so a slow or failed run can't overlap with the next one; the reschedule happens in a `finally`, so one bad night doesn't stop future runs.

**Format:** one JSON file per run — a JSON array of the raw `AuditLog` rows (Prisma `Date` fields serialize to ISO strings via `JSON.stringify`), uploaded to a single configured Drive folder. Filename: `audit-log-export_from-<ISO>_to-<ISO>.json` (colons/dots replaced with `-` for filename safety) — human-readable, but not parsed back to derive state (see cursor below).

**Incremental, cursor tracked in Postgres:** `AuditExportCursor` is a singleton row (`id` fixed to `"singleton"`, `lastExportedAt DateTime?`). Each run reads the cursor, queries `AuditLog` rows with `createdAt` in `(lastExportedAt, runStartedAt]`, and **only advances the cursor to `runStartedAt` after a successful upload** — so a failed run is retried (with overlap) on the next scheduled run instead of silently losing rows. `lastExportedAt = null` (no cursor row yet) exports the entire table (first-run bootstrap). Zero new rows since the cursor → the run logs and skips the upload without writing an empty file or advancing the cursor.

**Credentials — two env vars, optional (`src/config/env.ts`):**
- `GOOGLE_SERVICE_ACCOUNT_JSON` — the full contents of a Google Cloud service-account key file (Drive API enabled, `drive.file` scope), minified to one line. If present, `env.ts` validates it parses as JSON (`optionalJsonEnv`); `jobs/googleDrive.ts` separately validates the parsed object actually has `client_email`/`private_key` string fields before constructing the `google-auth-library` `JWT` client, since JSON-parseable isn't the same as shaped-correctly.
- `GOOGLE_DRIVE_FOLDER_ID` — the target Drive folder's ID. The folder must be shared with the service account's `client_email`, since service accounts have no meaningful personal Drive storage quota of their own.

**Both vars are optional — the backend boots fine without them.** `env.isGoogleDriveConfigured` is `true` only when both are set; `runAuditLogExport()` checks it first and, if unconfigured, `console.log`s a clear message and returns without touching the database or Drive. The daily scheduler (`src/jobs/scheduler.ts`) keeps firing regardless — each run is just a cheap no-op until both vars are set. This was changed from an original hard-required design (2026-09-07, see **Known issues / follow-ups**) because a fresh deploy shouldn't be blocked on Google Cloud setup just to serve requests. `src/__tests__/setup.ts` still seeds dummy values so the existing upload-path tests exercise the real flow; `env.test.ts` and `auditLogExport.test.ts` separately cover the unset/skip path.

**Google Drive API access:** `google-auth-library`'s `JWT` client (built directly from the parsed service-account credentials, scoped to `https://www.googleapis.com/auth/drive.file`) mints the bearer token via `getAccessToken()`; the upload itself is a plain `fetch` `POST` (multipart/related body: a JSON metadata part + a JSON media part) against the Drive v3 upload endpoint. Deliberately **not** the `googleapis` meta-package — that bundles generated clients for hundreds of unrelated Google APIs (Sheets, Calendar, Gmail, ...) to reach the one Drive `files.create` call this job needs; `google-auth-library` alone (which `googleapis` itself only re-exports for auth) plus one `fetch` call covers the same functionality with a much smaller dependency footprint. See `AUDIT-simplicity.md`'s 2026-09-07 finding for the reasoning that prompted this swap.

**Failure handling:** `runAuditLogExport()` throws on any failure (missing/invalid credentials, a DB error, a Drive API error) — it does not swallow anything itself. `scheduler.ts`'s `runAndReschedule()` is the single place that catches, `console.error`'s (never silent), and reschedules regardless of outcome. A failed night is visible in server logs and simply retried ~24h later; it never crashes or restarts the backend process.

## Buvette Cashier Frontend

`apps/buvette` — the till app BDE members use to operate the buvette on a tablet/phone. Requires an authenticated `Member` of any role (any tier, not bureau-only — same "any logged-in member" RBAC shape as the backend endpoints it calls). Scope: products, custom price, and the three payment modes (scan/cash/card). **Not built here** (separate future tasks): the recharge/top-up flow and the QR display/profile flow (both belong on the main site's profile tab), the actual SumUp integration, and the other 5 frontends.

**Structure:**
- `src/App.tsx` — auth gate: renders `screens/LoginScreen.tsx` if unauthenticated, else `screens/TillScreen.tsx`, driven by `@wave/auth-client`'s `useAuth` hook.
- `src/screens/TillScreen.tsx` — holds the current sale as a single `Sale` (`src/types.ts`): either `{ kind: "product", product, quantity }` or `{ kind: "custom", amountPoints }`, mutually exclusive (picking a product or entering a custom amount replaces the other, matching "custom price as a backup" from the spec). Renders the live product grid (`GET /products`, active-only) + custom amount entry, then — once a sale is set — the payment mode selector, then the chosen mode's flow component.
- `src/components/PaymentModeSelector.tsx` — large **Scan** button, small **Cash** button, **Card** button; exactly one mode per sale (picking a mode swaps to that flow, not additive).
- `src/components/ScanPaymentFlow.tsx`, `CashPaymentFlow.tsx`, `CardPaymentFlow.tsx` — one component per payment mode, described below.
- `src/lib/authClient.ts`, `products.ts`, `scan.ts` — thin wrappers around `@wave/auth-client`'s `authorizedFetch` for `GET /products` and `POST /buvette/scan`.

**QR scanning approach:** [`qr-scanner`](https://www.npmjs.com/package/qr-scanner) (the only new dependency added, scoped to `apps/buvette/package.json` only) — wraps `getUserMedia` camera access and decodes via the native `BarcodeDetector` where available, falling back to a bundled WASM decoder elsewhere. Chosen over the raw `BarcodeDetector` API alone because that API has no Safari/iOS support, and till operators may be on any device. With Vite as the bundler, the worker script resolves via qr-scanner's own automatic dynamic `import()` — **do not** manually set `QrScanner.WORKER_PATH` (an older pattern from qr-scanner's docs); doing so is a no-op in current versions and logs a deprecation warning.

**Payment mode behavior:**
- **Scan (points):** `ScanPaymentFlow.tsx` opens the camera, decodes a QR payload, and calls `POST /buvette/scan` with either `{ productId, quantity }` or `{ customAmount }` depending on the sale kind (see **Buvette Scan + Deduction** — both are supported server-side). Backend error statuses are mapped to operator-facing messages: 401 → invalid/expired QR, 402 → insufficient balance, 404/409 → product not found/inactive, 429 → duplicate scan.
- **Cash:** `CashPaymentFlow.tsx` is a **change-counting aid only** — no backend call. The operator enters the amount tendered; the app computes `change = tendered - total` and flags `tendered < total`. Confirmed with the project owner that this (not a bare total display) is the intended behavior.
- **Card:** `CardPaymentFlow.tsx` is a visible but explicitly disabled **"coming soon"** state — no backend call, since no SumUp integration exists yet (see **Buvette Scan + Deduction**'s Scope note). Selecting it shows why rather than silently doing nothing.

**React 18 StrictMode gotcha (verified live, not just read):** `ScanPaymentFlow`'s camera lifecycle needed a specific fix to work correctly under `pnpm dev`. `qr-scanner`'s `stop()`/`destroy()` clears the shared `<video>` element's stream via an internal, un-cancelable ~300ms-delayed timer. React 18 StrictMode (wrapping `App` in `main.tsx`) double-invokes effects in development — mount → cleanup → mount — and without a fix, the *first* (throwaway) scanner instance's delayed teardown timer fires *after* the second (real) instance has already attached its own live stream, silently killing it (the video renders visibly on screen but never produces decodable frames — confirmed via a real fake-camera Playwright test, not guessed). The fix: defer the actual `destroy()` call, and cancel it if the effect re-runs before it fires, reusing the still-live scanner instead of creating a second one. This only matters in development (StrictMode's double-invoke is a no-op in production builds), but `pnpm dev` is how this app is actually developed and tested day to day, so it's a real fix, not a cosmetic one.

**`packages/auth-client` and `packages/ui` were empty stubs before this work** — genuinely reusable content was built into them rather than duplicated into `apps/buvette` alone, per the project owner's explicit go-ahead:
- `packages/auth-client/src/`: `client.ts` (`createAuthClient(apiUrl)` — login/logout, localStorage-persisted session, auto-refresh via `/auth/refresh` before the access token expires, a pub-sub `subscribe` for reactivity, and `authorizedFetch` which attaches a valid bearer token and clears the session on an unexpected 401), `useAuth.ts` (a React hook wrapping the client), `tokenStorage.ts`, `types.ts`. Needed `react`/`@types/react` added as peer/dev deps and `jsx`+`DOM` added to its `tsconfig.json` (neither existed before — it had never actually been used from a `.tsx` file).
- `packages/ui/src/`: added `Button` (variant/size props, an `lg` size for touch targets) and `Banner` (success/error/info feedback) as the first real shared primitives; the pre-existing `Placeholder` export was left untouched.
- `packages/api-types/src/index.ts`: added `Product`, `ScanRequest`, `ScanResponse`, `ApiErrorResponse` — pure types shared between the backend contract and `apps/buvette`, no runtime code.

**Local dev gotcha (pre-existing gap, not fixed here):** none of the 6 frontend apps have a local dev source for `VITE_API_URL` — it's documented in **Deployment (production)** only as a Docker build ARG. Running `apps/buvette` locally therefore needs `VITE_API_URL=http://localhost:3000 pnpm --filter @wave/buvette dev` (or equivalent) until a real per-app `.env` convention is added; without it, the app's `fetch` calls resolve against relative paths and silently 404 against the Vite dev server itself. Also note: `apps/backend/.env`'s `CORS_ORIGINS` only listed `http://localhost:5173` (bureau's port) — it needs `http://localhost:5174` (buvette's port) added too for local testing across two frontends at once.

**Verification:** all three payment modes were exercised against the real backend + a local dev Postgres (not just mocks) — login, live product catalog (active-only filtering confirmed against a deliberately inactive seeded product), quantity stepper, custom amount entry, cash change calculation and completion, and the card "coming soon" state were all confirmed working via a real headless-browser run (Playwright + system Chrome). The scan mode's full camera → decode → deduct round trip was validated in two parts instead of one end-to-end run: the `POST /buvette/scan` contract itself (success for both `productId` and `customAmount`, 401 invalid QR, 402 insufficient balance, 429 replay guard) was confirmed live via direct calls with a real seeded QR token and real balance deduction in Postgres; the camera-to-decode leg was validated up to (but not including) a successful decode — a fake-camera-device Playwright test correctly exercised the full permission/lifecycle path (including finding and fixing the StrictMode bug above) and visibly rendered the QR in the video feed, but a full automated decode couldn't be forced through in this sandboxed headless-Chrome environment (a canvas/video frame-sampling limitation of headless Chrome with a synthetic camera device, not an application defect). This is the same category of acknowledged gap as SumUp being untestable without live credentials — a human tester with a real device/camera should do one live scan before this ships.

## SumUp Integration + Recharge

Implemented in `apps/backend/src/lib/sumup.ts` (the shared SumUp client) and `apps/backend/src/routes/me.ts` (`POST /me/recharge`, `POST /me/recharge/:id/confirm`), mounted alongside `GET /me/qrcode` under the existing `/me/...` self-service convention. Tests: `src/__tests__/lib/sumup.test.ts` (mocked `fetch`, no live network) and the recharge cases in `src/__tests__/routes/me.test.ts` (mocked Prisma + mocked `sumup.ts`).

**Scope correction, 2026-09-11:** a task to add this recharge endpoint originally assumed a SumUp Cloud API integration and a points-to-currency conversion already existed from an earlier till/card-payment task. Neither did — `CardPaymentFlow.tsx` (see **Buvette Cashier Frontend**) is still an unwired "coming soon" placeholder, and no SumUp code existed anywhere in the repo or its history. `src/lib/sumup.ts` is therefore the **first** SumUp integration in this codebase, built as this task's prerequisite — scoped deliberately narrow to what a recharge flow and a future till card flow can both reuse (OAuth, conversion, checkout creation, confirmation polling). **Not built here**, and still open: the till's physical card-reader pairing and `CardPaymentFlow.tsx`'s wiring — that's the SumUp *Readers API* (`POST /v0.1/merchants/{merchant_code}/readers/{id}/checkout`), a different endpoint family from the *Checkouts* API this module uses, since a till has an operator-controlled physical reader in the room while a self-service recharge does not. Only OAuth token handling, the points↔currency conversion, and the confirmation-polling shape are guaranteed shared between the two — a future till integration must reuse `getAccessToken`'s pattern and `pointsToAmountMinorUnits()` rather than redefining either, but will need its own reader-checkout create call.

**Conversion rate:** 15 points = €1 (`POINTS_PER_EUR` in `sumup.ts`), confirmed with the project owner — the only points↔currency peg defined anywhere in this app (previously an open question, see **Open questions**' now-resolved "Points vs. real currency" item below). `pointsToAmountMinorUnits(points)` returns cents, rounded to the nearest cent (`Math.round(points * 100 / 15)`). Any future payment flow must reuse this function rather than defining its own rate.

**Recharge amount model: free integer amount, not fixed presets.** A member requests any integer number of points (`POST /me/recharge` body: `{ points }`), bounded 1–3000 (`MIN_RECHARGE_POINTS`/`MAX_RECHARGE_POINTS` in `me.ts`, a sanity cap against fat-finger/abuse, not a business rule — adjust freely). Chosen over fixed presets because it needs no new catalog concept and mirrors the `customAmount` fallback `POST /buvette/scan` already established for points-based charges.

**Confirmation pattern: two-endpoint create+confirm, polled by the (future, not-built-here) frontend — no webhooks.** SumUp's hosted checkout is inherently redirect-based (the payer leaves to a SumUp-hosted page), so it cannot be resolved synchronously in one request, and no webhook receiver exists anywhere in this codebase (one would need its own signature verification and idempotency handling this task didn't build). This is the first confirmation mechanism established in this app; any future till confirmation should reuse this shape rather than inventing a second one.
- `POST /me/recharge` — creates a `RechargeCheckout` row (status `PENDING`) and a SumUp hosted checkout (`hosted_checkout.enabled: true`, `valid_until` 30 minutes out — mirrors the QR token's TTL discipline, see **Per-User QR Code**). No points credited yet. Returns `{ rechargeId, checkoutId, hostedCheckoutUrl, points, amount, currency }`.
- `POST /me/recharge/:id/confirm` — safe to call repeatedly (idempotent): does **one** live SumUp status check per call. `PENDING` → `202` (call again later, no state change). `FAILED`/`EXPIRED` → the row is flipped and `402` returned, no credit. `PAID` → inside `prisma.$transaction`, a conditional `rechargeCheckout.updateMany({ where: { id, status: "PENDING" }, ... })` guards against a concurrent confirm call double-crediting (exact same race-safety idiom as `buvette.ts`'s balance deduction), then `PointsAccount.balance` is incremented and a `Transaction` (`type: "TOPUP"`, positive `amount`, `performedById: null` — same reasoning as buvette purchases, see **Buvette Scan + Deduction** — since this isn't a manual staff adjustment) is created. Calling `confirm` again after a row already left `PENDING` just replays the stored outcome — no second SumUp call, no second credit.

**Self-identification:** both routes resolve the caller purely from `req.auth!.sub` (the JWT) — never from anything in the request body or URL — exactly like `/me/qrcode`. `confirm` additionally checks the requested `RechargeCheckout.pointsAccountId` matches the caller's own `PointsAccount.id` before touching it (404 if not, same generic non-revealing shape as a genuinely-missing id) — verified live against a real dev Postgres: one member's token could not confirm another member's `RechargeCheckout` row, and the other account's balance was unaffected. Same **Known gap** as `/me/qrcode`: only `Member`s can authenticate today, so plain students can't self-recharge yet either.

**Configuration:** `SUMUP_CLIENT_ID`/`SUMUP_CLIENT_SECRET`/`SUMUP_MERCHANT_CODE`, all optional (`src/config/env.ts`, `env.isSumUpConfigured`) — exact same "boots fine without them" pattern as the Google Drive vars (see **Audit Log Export**), since no real SumUp account exists yet either. `POST /me/recharge` returns `503 { error: "recharge is not available yet" }` when unconfigured, instead of failing at startup.

**No new dependency:** `sumup.ts` is OAuth2 client-credentials (`POST https://api.sumup.com/token`) plus plain `fetch` calls to the Checkouts API (`POST`/`GET https://api.sumup.com/v0.1/checkouts`), mirroring `googleDrive.ts`'s "auth then fetch" shape rather than pulling in a SumUp SDK.

**Verified:** full mocked test suite (`sumup.test.ts`, `me.test.ts`'s recharge cases) plus `pnpm run build`/`pnpm run lint`. Also exercised live against a real dev Postgres: the unconfigured-503 path, request-body validation ordering, a real (negative-path) network round trip to `api.sumup.com` with placeholder credentials confirming the OAuth call actually fires and a failure cleanly 502s with no `RechargeCheckout` row left behind, and the cross-account ownership check on `confirm` described above. The `PAID` happy path itself is untested against a live SumUp sandbox — no real SumUp credentials exist yet, same category of gap as the till's card mode being "untestable without live credentials" (see **Buvette Cashier Frontend**).

**Not built here (separate future tasks):** the recharge/profile frontend (profile tab, "recharge points" UI, redirect-to-hosted-checkout handling, polling `confirm`) and the till's physical card-reader pairing + `CardPaymentFlow.tsx` wiring (SumUp Readers API — see the scope-correction note above).

## Security hardening

App assembly lives in `apps/backend/src/app.ts` (`createApp()`, exported for testing — see `src/__tests__/app.test.ts`), imported by `src/index.ts`, which only calls `.listen()` and owns process-level shutdown. `src/app.ts` imports `./config/env.js` as its own first line (not just relying on `index.ts`'s), so the fail-fast secret check can't accidentally run after some other import that itself needs a DB connection.

Cross-cutting, applied globally in `createApp()` (not specific to any one route):
- `helmet()` is applied first, before `express.json()`, for standard security headers (CSP, HSTS, `X-Content-Type-Options`, etc.).
- `cors({ origin: env.corsOrigins })` runs right after `helmet()`, before `express.json()`/routers. `CORS_ORIGINS` is a required env var (comma-separated, parsed once in `config/env.ts`, same fail-fast pattern as the JWT secrets) — no hardcoded origin list in code. No credentials/cookies mode needed since auth is Bearer-token only.
- `app.set("trust proxy", 1)` — trusts exactly one hop: the shared edge Caddy instance this backend sits behind in production (see **Deployment (production)** below). Needed so `req.ip` (used by rate limiting and the audit log's `ipAddress` field) reflects the real client IP instead of the proxy's. Set to `1`, not a boolean/wildcard — raising this without confirming the real proxy chain would let a client spoof its own IP via `X-Forwarded-For`.
- `express.json({ limit: "100kb" })` — an explicit body-size limit (matches the library's own default; made explicit so it's a deliberate choice, not an implicit one).
- A generic error-handling middleware is registered last (after all routers). It never leaks a stack trace or `err.message` to the client, regardless of `NODE_ENV` (Express's own default handler leaks the stack trace whenever `NODE_ENV !== "production"`, which would otherwise apply to local dev and CI test runs — the Docker runtime image sets `NODE_ENV=production`, but `pnpm dev` and CI don't). It does forward a genuine 4xx status when the error already carries one (`err.status`/`err.statusCode` in the 400-499 range — e.g. `express.json()`'s malformed-JSON `SyntaxError`, or a body exceeding the limit above) as `{ error: "bad request" }`, falling back to `500 { error: "internal server error" }` only for everything else — a client mistake is no longer reported as a server failure.
- `SIGTERM`/`SIGINT` handlers (in `index.ts`) close the HTTP server and call `prisma.$disconnect()` before exiting, instead of leaving Prisma to be torn down mid-request on container stop.
- `/auth/login` has rate limiting (10/15min/IP); `/auth/refresh` and `/auth/logout` share a looser 30/15min/IP limiter — see **Authentication** above. Both limiters are constructed inside `createApp()`, so tests get isolated state per app instance.
- The `apps/backend/Dockerfile`'s `build` stage runs `pnpm --filter @wave/backend run prisma:generate` before compiling — without it, a fresh `docker build` fails the same way a fresh CI checkout used to (see **Known issues / follow-ups**): `@prisma/client`'s postinstall can't find `schema.prisma` at its non-default workspace path and silently no-ops. The runtime image no longer ships devDependencies or compiled test files: a `prod-deps` stage runs `CI=true pnpm -C apps/backend prune --prod` on top of the already-built `build` stage (pruning in place, rather than a second full install, so the already-generated Prisma Client survives — a fresh `--prod`-only install would never regenerate it, since the `prisma` CLI is itself a devDependency); separately, `apps/backend/tsconfig.build.json` (extends `tsconfig.json`, excludes `src/**/__tests__/**`) is what `package.json`'s `build` script actually emits from (`tsc -p tsconfig.json --noEmit && tsc -p tsconfig.build.json` — the first invocation still type-checks tests, the second just doesn't emit them), so `dist/__tests__` no longer exists. Both were verified against a real `docker build` + `docker compose up` boot (not just read): confirmed `require.resolve('vitest')` fails and `require.resolve('express')`/`require.resolve('@prisma/client')` succeed inside the built image, `dist/__tests__` is absent, and `/health` responds `200` end to end against the real Postgres service. Note: `pnpm -C apps/backend prune --prod` (unlike a plain unscoped `pnpm prune --prod`, which reads the *workspace root's* manifest and — verified by testing — deletes prod dependencies too) only removes the per-project symlinks; the underlying pnpm content-addressable store (`node_modules/.pnpm`) still physically retains the pruned packages' files, so this closes the *reachability*/import-surface gap but doesn't meaningfully shrink image size on disk.

**Not done, and deliberately so:**
- No outbox/durability mechanism for audit log writes — see **Audit Logging**'s fire-and-forget behavior above. Out of scope without a queue.

## Deployment (production)

Repo-level prep for deploying onto a **shared** Debian machine (not a dedicated VPS) that already hosts other projects (e.g. "dolibarr") — originally done 2026-09-07, corrected the same day, and corrected again 2026-09-07 once the real shared-machine setup (edge Caddy + cloudflared tunnel, `edge` network convention, a `db`-named backup-script dependency) was described (see **Known issues / follow-ups**). This is config/documentation only: nothing has been executed, connected to, or configured on any real machine yet, and no CI/CD auto-deploy exists. See `DEPLOY.md` for the manual checklist of what still has to happen on the actual machine.

**Reverse proxy: a shared edge Caddy instance, not one this repo runs.** The machine runs one Caddy container as the edge for *every* hosted project, one `.caddy` site file per project under `/opt/proxy/caddy/sites/` (e.g. `dolibarr.caddy`). This repo never creates or edits those files — `deploy/sites.reference.caddy` is a best-effort, non-deployed sketch of what this project's site file(s) should contain, for a human to adapt and place there manually (`DEPLOY.md`).

**TLS: terminated upstream by an existing cloudflared tunnel — not by Caddy, not DNS-01/ACME, not anything in this repo.** The domain is a wildcard, `*.bde-wave.com`; each frontend plus the backend gets its own subdomain (`api.`, `bureau.`, `buvette.`, `comm.`, `events.`, `partenariats.`, plus the apex for showcase). Because the tunnel already handles certs end-to-end, the shared Caddy's site blocks are plain `http://` reverse proxies — no `tls`/DNS provider config needed at all, which is why the earlier DNS-01/Cloudflare-API-token design (`CF_API_TOKEN`, `deploy/wave.caddy`'s `tls { dns cloudflare ... }` block) no longer applies and was removed.

**Docker networking: `edge` (external, shared) + `internal` (this project's own).** `docker-compose.prod.yml` defines two networks: `edge` — a **fixed-name**, pre-existing `external: true` network (not a placeholder like the old `CADDY_EXTERNAL_NETWORK` var — this machine's convention is that every reverse-proxied container just joins a network literally named `edge`) — and `internal`, a plain bridge network owned by this compose file, for Postgres. `backend` joins both (needs `edge` to be reachable by the shared Caddy, `internal` to reach Postgres); each of the 6 frontend containers joins `edge` only; `db`/`migrate` join `internal` only, so Postgres is never reachable from the shared edge network regardless of any Caddy config.

**Postgres naming matches an external backup script's expectations.** `/opt/proxy/backup.sh` (outside this repo, never modified by it) expects the Postgres service to be named `db` to detect and back it up — so the compose service is `db` (container `wave-db`), not `postgres`, and its volume is `wave_db`, not `postgres_data`.

**A one-shot `migrate` service runs `prisma migrate deploy` before `backend` starts.** Built from `apps/backend/Dockerfile`'s `build` stage (`target: build`), not `runtime` — the runtime image prunes devDependencies (see **Security hardening** above), so the `prisma` CLI isn't in it, but the `build` stage still has it and has already run `prisma generate`. `backend`'s `depends_on` requires `migrate: condition: service_completed_successfully` in addition to `db: condition: service_healthy`, so the backend never starts against an un-migrated schema.

**All 6 frontends are Dockerized and deployed**, not just showcase/bureau/buvette — `apps/<app>/Dockerfile` for each (`showcase`, `bureau`, `buvette`, `pole-comm`, `pole-events`, `pole-partenariats`), one shared multi-stage template (base/deps/build/runtime, matching the backend Dockerfile's shape) differing only in which `@wave/<app>` package it builds. The `runtime` stage is `caddy:2-alpine` serving the static `dist/` output with SPA fallback via one shared `deploy/frontend.Caddyfile` (`try_files {path} /index.html`), copied identically into all 6 images. `VITE_API_URL` (the backend's public URL) is delivered as a **Docker build ARG**, threaded into `ENV VITE_API_URL=$VITE_API_URL` before `vite build` runs — not an `apps/<app>/.env.production` file, because both `.gitignore` and `.dockerignore` have a bare (non-path-anchored) `.env.production` pattern that would silently exclude such a file from both git and the Docker build context. Vite exposes env vars already present in `process.env` when it runs with the same `import.meta.env.VITE_*` mechanism as `.env`-file-sourced ones (highest priority, confirmed against Vite's own docs), so no extra Vite config was needed — `apps/<app>/src/lib/api.ts` just reads `import.meta.env.VITE_API_URL`. Each app also got a standard `src/vite-env.d.ts` (`/// <reference types="vite/client" />`), missing from the original scaffold, without which `import.meta.env` doesn't typecheck.

**CORS is enforced** (`CORS_ORIGINS`, required — see **Security hardening** above) since the backend is now served from a different subdomain (`api.bde-wave.com`) than every frontend calling it.

**Env vars, production (`.env.production.example`, root):** `POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB` (no defaults, unlike dev), `BACKEND_PORT`, `JWT_SECRET`/`JWT_REFRESH_SECRET`, `CORS_ORIGINS` (all required — the stack refuses to boot without them); `GOOGLE_SERVICE_ACCOUNT_JSON`/`GOOGLE_DRIVE_FOLDER_ID` (optional — see **Audit Log Export** above); `VITE_API_URL` (a Docker build ARG for the 6 frontend images, not a runtime var). `DOMAIN` is kept as a comment-only line (documents the wildcard `*.bde-wave.com`) since nothing in this repo reads it anymore — no repo-owned Caddy config is left to substitute it into. `CF_API_TOKEN` was removed entirely (no DNS-01 challenge exists anymore). `.env.production` itself is git-ignored.

**Unresolved before actual deployment:** whether `/opt/proxy/backup.sh` matches Postgres by service name, container name, or volume name specifically — `db`/`wave-db`/`wave_db` all line up with the stated convention, but this hasn't been confirmed against the script's actual matching logic (it lives outside this repo and wasn't read). The exact shared Caddyfile's `import` snippet name for common headers is also unconfirmed — `deploy/sites.reference.caddy` uses a placeholder (`import common`) pending a look at the real file on the machine. See `DEPLOY.md` for the full manual checklist.
